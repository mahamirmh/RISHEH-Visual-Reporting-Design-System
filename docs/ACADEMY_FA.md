# آکادمی گزارش‌دهی و طراحی بصری ریشه
## دوره خودآموز با مثال واحد، توضیح اصطلاحات و تمرین

**مخاطب:** طراح، توسعه‌دهنده، مدیر پروژه، کارشناس محتوا و QA. **پیش‌نیاز:** ندارد. **زمان پیشنهادی:** ۹۰ تا ۱۲۰ دقیقه. **داده‌ها:** همگی ساختگی.

![نقشه یادگیری](../assets/learning-path.svg)

## درس ۱ — Brief یا بریف: تعریف مسئله پیش از طراحی

**تعریف:** بریف سند کوتاهی است که هدف، مخاطب، سؤال اصلی، محدودیت، ورودی و خروجی مورد انتظار را روشن می‌کند. بریف **خود طراحی نیست**؛ توافقی درباره چیزی است که باید طراحی شود.

**مثال آوا:** «مدیر محصول می‌خواهد بداند آیا تعداد درخواست‌های ثبت‌شده در سه ماه گذشته بیشتر شده است. گزارش باید فارسی، قابل مشاهده در موبایل و همراه با داده اصلی باشد.»

**اجزای بریف خوب:** مخاطب، تصمیم مورد انتظار، سؤال، داده، بازه، محدودیت و معیار موفقیت.

**اشتباه رایج:** «یک داشبورد قشنگ بساز» بریف کافی نیست، چون مسئله و معیار موفقیت ندارد.

## درس ۲ — Blueprint یا نقشه کلان

**تعریف:** بلوپرینت نقشه‌ای است از اجزای سیستم و ارتباط آن‌ها. می‌تواند معماری فنی، نقشه تجربه یا نقشه تولید گزارش باشد؛ بنابراین با «نقشه ساختمان» یا «وایرفریم» یکی نیست.

![معماری نمونه](../assets/architecture.svg)

**مثال:** فایل داده → بررسی صحت → انتخاب نوع نمایش → ساخت صفحه → PDF/Word. این نقشه توضیح می‌دهد **اجزا چگونه همکاری می‌کنند**، نه اینکه دکمه‌ها دقیقاً کجای صفحه‌اند.

## درس ۳ — Chart، Graph و Diagram چه تفاوتی دارند؟

![مقایسه نمایش داده و فرایند](../assets/visual-vocabulary.svg)

**Chart / چارت:** نمایش سازمان‌یافته داده، معمولاً کمی؛ مثل نمودار تعداد درخواست‌ها.

**Graph / گراف:** در تحلیل داده می‌تواند همان نمودار مختصات باشد؛ در علوم کامپیوتر گراف شبکه‌ای از «گره» و «یال» است. همیشه با توجه به زمینه معنا را مشخص کن.

**Diagram / دیاگرام:** تصویر توضیحی روابط، ساختار یا روند؛ الزاماً داده عددی ندارد.

**Flowchart / فلوچارت:** نوعی دیاگرام برای نمایش ترتیب مراحل و تصمیم‌ها. لوزی معمولاً تصمیم، مستطیل فعالیت و پیکان مسیر حرکت را نشان می‌دهد.

**مثال:** «۱۲، ۱۸، ۲۴ درخواست» یک چارت خطی می‌خواهد؛ «ثبت → بررسی → تأیید یا رد» فلوچارت می‌خواهد.

## درس ۴ — جدول، KPI، داشبورد و اسکورکارت

**Table / جدول:** مقادیر دقیق را در سطر و ستون نشان می‌دهد؛ برای مقایسه جزئیات یا دسترسی‌پذیری ضروری است.

**KPI / شاخص کلیدی عملکرد:** معیاری که مستقیماً به هدف مرتبط است؛ هر عددی KPI نیست. «تعداد درخواست» زمانی KPI است که هدفی مرتبط با آن تعریف شده باشد.

**Dashboard / داشبورد:** نمای یکپارچه چند شاخص برای پایش وضعیت یا تصمیم سریع.

**Scorecard / کارت امتیاز:** عملکرد واقعی را در برابر هدف، معیار یا دوره مقایسه می‌کند.

**مثال:** ۲۴ درخواست = Metric. هدف ۳۰، تحقق ۲۴، اختلاف ۶ = Scorecard. کنار هم گذاشتن روند، خطا و شاخص‌ها = Dashboard.

## درس ۵ — Wireframe، Mockup و Prototype

**Wireframe / وایرفریم:** اسکلت کم‌جزئیات صفحه برای تعیین جای محتوا، ترتیب و مسیرها؛ هنوز درباره زیبایی نهایی تصمیم قطعی نمی‌گیرد.

**Mockup / موکاپ:** تصویر نسبتاً نهایی صفحه با رنگ، تایپوگرافی، تصاویر و فاصله‌ها؛ ممکن است هیچ تعاملی نداشته باشد.

**Prototype / پروتوتایپ:** نمونه‌ای برای آزمایش رفتار و مسیر تعامل؛ ممکن است از نظر ظاهر ساده یا بسیار نزدیک به محصول نهایی باشد.

**نکته:** موکاپِ داخل قاب موبایل صرفاً «نمایش» است، نه اثبات اینکه طراحی واقعاً روی موبایل کار می‌کند.

## درس ۶ — انتخاب نمودار با سؤال درست

![درخت تصمیم](../assets/visual-decision-tree.svg)

| سؤال | نمایش مناسب | دلیل | از چه چیزی پرهیز کنیم؟ |
|---|---|---|---|
| تغییر در زمان؟ | Line | پیوستگی روند | Pie برای زمان |
| مقایسه دسته‌ها؟ | Bar | طول میله قابل مقایسه است | 3D و تزئینات |
| مقدار دقیق؟ | Table | عدد قابل خواندن است | فقط نمودار |
| سهم از یک کل؟ | Pie فقط برای چند بخش مثبت | نمایش نسبت | سهم‌های منفی یا تعداد زیاد |
| ترتیب رویدادها؟ | Timeline | زمان و ترتیب | نمودار عددی بی‌دلیل |
| تصمیم و انشعاب؟ | Flowchart | مسیرهای شرطی | فهرست خطی بدون شاخه |

**مثال آوا:** سه مقدار ماهانه ۱۲، ۱۸، ۲۴ → Line؛ مقایسه کانال‌های ورودی در یک ماه → Bar.

## درس ۷ — Visual Hierarchy و Progressive Disclosure

**Visual Hierarchy / سلسله‌مراتب بصری:** استفاده هدفمند از اندازه، کنتراست، فاصله و جایگاه برای هدایت توجه. ترتیب پیشنهادی: پاسخ اصلی → شواهد → جزئیات.

**Progressive Disclosure / آشکارسازی تدریجی:** جزئیات تکمیلی را در زمان نیاز نشان می‌دهیم؛ مثلاً نمودار ابتدا دیده شود و جدول اعداد با بازکردن بخش «مشاهده داده‌ها» نمایش داده شود. اطلاعات ضروری را نباید پنهان کرد.

**خطای رایج:** ده کارت هم‌اندازه بدون عنوان معنادار، به کاربر نمی‌گویند کدام مهم‌تر است.

## درس ۸ — Data Provenance، Accessibility و RTL

**Data Provenance / منشأ داده:** اینکه عدد از کجا آمده، در چه زمانی استخراج شده و چگونه محاسبه شده است. منبع و تاریخ استخراج باید قابل ردیابی باشند.

**Accessibility / دسترس‌پذیری:** استفاده با صفحه‌خوان، صفحه‌کلید، بزرگ‌نمایی و بدون اتکا به رنگ. برای نمودار عنوان و جدول جایگزین ارائه کن.

**RTL / راست‌به‌چپ:** جهت متن فارسی است، نه الزاماً وارونه‌کردن همه نمودارها، اعداد، URLها یا محور زمان. متن‌های دوزبانه باید جداگانه بررسی شوند.

## درس ۹ — از محتوا تا خروجی واقعی

۱. سؤال تصمیم را بنویس. ۲. داده و منبع را جمع کن. ۳. ساختار Report IR را آماده کن. ۴. اعتبارسنجی کن. ۵. در React یا سند خروجی بگیر. ۶. محتوا و ظاهر را کنترل کن.

**Report IR / مدل میانی گزارش:** قرارداد داده مستقل از نحوه نمایش؛ یعنی یک بار محتوا را تعریف می‌کنیم و خروجی‌های مختلف آن را تفسیر می‌کنند. [راهنمای توسعه‌دهنده](DEVELOPER_GUIDE_FA.md).

## درس ۱۰ — تحویل حرفه‌ای و معیار پذیرش

گزارش فقط زمانی آماده تحویل است که سؤال مخاطب را پاسخ دهد، داده‌ها قابل ردیابی باشند، نمایش اشتباه نداشته باشد، نسخه موبایل قابل استفاده باشد و خروجی‌های فارسی به‌صورت واقعی بررسی شده باشند.

**تمرین پایانی:** یک بریف برای محصول خیالی آوا بنویس؛ یک جدول و نمودار مناسب انتخاب کن؛ یک فلوچارت ثبت درخواست پیشنهاد بده؛ توضیح بده چرا این سه خروجی متفاوت‌اند. پاسخ نمونه در [کاربرگ تمرین](WORKBOOK_FA.md) است.
